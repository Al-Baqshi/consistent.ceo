Consistent CEO · gateway remediation

Gateway Hardening Plan

Seven phases, each one a branch off main that compiles, passes the full test suite, and is releasable on its own. Ship them in order: every phase makes the next one either safer or cheaper.

Verified against 8bc455ae Date 2026-09-13 Status Phases 1–2 landed · ab489569 Diagnosis architecture review

The goal

The product's promise is unattended execution: loops pick up work, run a real coding agent, and report evidence with nobody watching. That promise has exactly four structural requirements, and none of them is fully met today.

Liveness
No loop can stop silently. A dead loop is indistinguishable from an idle one — the gateway keeps answering /health either way.
Freshness
No loop acts on stale state. Read, release, await, write-by-position is the shape of every concurrency bug in this tree.
Durability
Nothing deletes data it has not read. A failed read must never be laundered into a delete.
Singularity
One definition per rule. A rule written in four places is four rules that will drift apart.

Phases 1–4 buy those four properties. Phases 5–7 remove the structural reasons they were easy to violate in the first place.

Four corrections to the review first

The review was right about the shape of the problem and wrong in four details. A plan built on bad premises fixes the wrong things, so these are settled before the phases start.

The review claimedWhat the code actually does
Reminders double-fire Not true. reminders.rs:266-296 scans, marks reminder_fired, and completes under a single write guard — atomic within a process. The real defect is narrower: metadata_fired reads as_bool() while chat_tools.rs:1404 writes the string "false". Harmless today, breaks the day anything writes "true". → Phase 7.
Heartbeat beats double-run Mostly not true. heartbeat_store.rs:263 claims a beat with a conditional UPDATE … WHERE lease_until IS NONE OR lease_until < $now — genuinely atomic. The gap is a fixed ten-minute lease that is never renewed; a longer dispatch gets re-fired. → Phase 7.
The mission engine dies permanently on its third restart Worse than stated. No such counter exists anywhere. All nine loops are spawned with a bare tokio::spawn whose handle is discarded. One panic kills that loop for the life of the process, with no restart and nothing user-visible. → Phase 1, now the highest-severity item.
Four disagreeing mission tallies One canonical helper — derive_mission_task_counts at orchestrator.rs:50. But eighteen other sites filter tasks by mission_id inline, so it is canonical in name only. → Phase 7.

Why this order

The sequence is not a priority list — each arrow is a real handoff. Phase 2 can be attempted first, but its mistakes would be invisible until Phase 1 lands.

The seven phases

Every phase ends in a mechanical gate — a test or a repo-health.sh breach — landed in the same commit as the fix it guards. A gate added later never runs against the code that needed it.

1landed

The process cannot silently stop

Two ways the gateway stops doing work while still reporting healthy.

What is broken

  • No loop supervision. main.rs:1393-1538 spawns nine loops and discards every handle. Tokio catches the panic, the task ends, nothing logs at loop level, the operator feed stays quiet. A panicking orchestrator means unattended execution silently ceases — the exact failure the product exists to prevent.
  • An ABBA deadlock between the two hottest paths. state.rs:1838 snapshot() takes 28 read guards as temporaries in a tail-position struct literal, so temporary lifetime extension keeps all of them alive to the end of the function — entities second, operator_feed sixteenth. state.rs:1937 takes operator_feed.write() into a named binding, holds it across two awaits, and takes entities.read() in the middle — the reverse order. Tokio's RwLock is write-preferring, so a pending writer blocks new readers and the cycle closes. Both paths run constantly.

The change

  • New supervisor.rs: spawn_supervised(name, policy, factory) distinguishes clean exit from JoinError::is_panic(), restarts with capped backoff, and pushes an operator-feed row per restart so a crash-looping subsystem is visible rather than inferred from silence. Convert all nine spawns.
  • Rewrite snapshot() to clone field by field, each guard dropped before the next is taken. This also dissolves the 28-guard convoy that serialises the snapshot against every writer.
  • Scope the feed write guard to the push-and-trim and drop it before the Surreal await; read entities afterwards.
  • Add a //! Lock order block to state.rs: never hold a guard across an await, never hold two.

Exit gate — all met

  • tests/loop_supervision_test.rs (3) — a loop that panics twice restarts twice and runs; /health reports degraded plus per-loop counts; a registry-less state omits the field rather than faking it.
  • supervisor.rs unit tests (6) — restart-and-record, clean return is not a restart, aborting supervision stops the loop, payload extraction, capped backoff, and that public counts carry no panic text.
  • The deadlock guard was verified to fail against the original code — it hangs the full 20s — and to pass against the fix.
  • repo-health.sh §7 now reports 11 background loops supervised, 0 with a discarded handle.
  • Workspace gates clean: check, clippy -D warnings, 1,607 tests passing.

What changed from this plan, and why

  • The first version of the deadlock test was worthless — written as planned, it passed against the broken code. Both paths take entities for read, and read guards are shared, so two paths in opposite orders cannot block each other. The cycle needs a third task queuing entities.write(), which is what makes a write-preferring RwLock block the reader in the middle. Adding that third actor reproduced the hang. Same severity — all three run constantly — but the review's mechanism was wrong.
  • Eleven loops, not nine. The two the review missed are the worst: the 60s control-state persist loop (nothing reaches disk or Surreal again, no symptom until a restart reads a stale snapshot) and the credential-vault sweeper (vaults stay unlocked in memory for the life of the process — a security regression, not a missed convenience).
  • No new feed kind. A crashed subsystem is system health, not work on a timeline, and a new kind would fire a phone push for an infrastructure event. Restart counts go on /health instead; panic text stays off that public endpoint and waits for Phase 4's authenticated store report.
  • Restarts are unlimited, alerts are throttled to one per five minutes per loop. Giving up after N failures would restore exactly the silence this phase removes.

2landed

One way to move a task

62 tasks.write() sites. Six are in state.rs; the other 56, across 25 files, each re-implement the same three steps and disagree about the rules.

What is broken

  • Write-by-stale-index. orchestrator.rs:340 collects (index, …) under a read guard and drops it. :395 awaits one Surreal recall per candidate entity holding no lock. :449 takes the write guard and mutates tasks[i] by that index with no re-check of identity or status. In between, any of 56 writers can push or retain — entity_import_api.rs:1136 deletes an entity's tasks and shifts every later index. Two outcomes: the wrong task is hijacked into an unattended agent run, including one the human just cancelled, or the index is out of bounds and the loop panics. :457 also reads the id after mutating, so the log names the wrong task.
  • The cancel guard is bypassed on the failure path. orchestrator.rs:674-681 re-finds by id correctly, then assigns t.status = Failed raw, ignoring set_task_status_guarded. A run that fails after the human cancelled overwrites Cancelled.
  • Chat reverts concurrent loop writes. chat_tools.rs:1417-1424 does *slot = task.clone() — a whole-row overwrite of a snapshot taken before an LLM round-trip.
  • 21 raw .status = TaskStatus:: assignments outside state.rs across 8 files, against 11 sites that use the guard.

The change

  • ControlState::update_task(id, f) — takes the write guard, re-finds by id, applies the closure, returns the updated clone for persistence. Position-based mutation stops being expressible.
  • Orchestrator pickup selects a candidate id, not an index, and re-asserts the status is still Backlog | Queued inside update_task. This single change closes the stale index, the panic, and the cancel hijack together.
  • Split the setter by actor instead of picking a default. The doc comment at state.rs:141-153 is right that one default cannot serve both — human reopen and requeue legitimately un-cancel. So: set_task_status_by_loop (guarded, #[must_use]) and set_task_status_by_human (unguarded). Renaming both forces all 56 sites to declare which actor they are.

Exit gate — all met

  • repo-health.sh §8 — three checks, each verified to fire against a deliberate violation before being kept: a task written by saved index, a direct task.status = assignment, and a ratchet on the remaining tasks.write() sites. Test fixtures and comments are skipped.
  • tests/orchestrator_failure_tests.rs — a runner crash after a human cancel leaves the task cancelled. Verified to fail against the old code with left: Failed, right: Cancelled.
  • Five new state.rs tests, including one that shows the indexed write landing on the wrong task after a retain, beside the update_task call that cannot.
  • Workspace gates clean: 1,618 tests passing.

What changed from this plan, and why

  • The tasks.write() breach became a ratchet, because a blanket ban was the wrong gate. 38 production sites remain and nearly all are already correct — they take the guard, then re-find by id, which is what update_task does internally. Banning them would have meant 36 cosmetic conversions riding along with three real fixes. The two patterns that actually caused defects are hard breaches instead, and neither has a production instance left.
  • The setters split by actor, not by strictness. The plan said make the guarded one the only setter; the existing doc comment was right that this cannot work, because reopen and requeue legitimately un-cancel. Naming the actor forces the choice at every call site instead.
  • A second bug fell out of the conversion: assigning task.status skips status_changed_at and completed_at — and the consistency streak and per-day counts are computed from exactly those fields.
  • claim_task joined update_task. Select, do I/O, then claim is the shape every loop needs and none had; leaving the status re-check to each caller would have rebuilt the original problem one loop at a time.

3

Nothing deletes what it has not read

Three persistence mechanisms, three boot reconciliation policies — and the destructive one is the default for entities.

What is broken

  • entity_store.rs:317-355 sync_all() upserts every in-memory entity, then selects the table and deletes every row whose id is absent from memory.
  • main.rs:1020 treats hydration failure as warn!-and-continue. So a transient Surreal read error at boot leaves memory empty, and the next periodic sync deletes the rows that failed to load. A read failure is laundered into permanent data loss.
  • task_store.rs:1-19 already documents the correct policy for the identical problem — "upsert-only periodic sync, so an instance that doesn't know a task yet can't delete it" — and entities never got it.

The change

  • sync_all becomes upsert-only. Pruning moves to an explicit prune_absent(keep), callable only from a path that can prove its read succeeded.
  • Hydration failure stops being advisory: a store that fails to hydrate is marked degraded and its periodic sync is disabled for the process lifetime. A gateway running on data it could not read must not write back.
  • Write the single reconciliation policy into ARCHITECTURE.md, including the honest split between row-backed collections and snapshot-only ones, so the next store author inherits a rule rather than a coin flip.

Exit gate

  • Test: a store whose list_all returns Err at boot performs zero deletes afterwards.
  • repo-health.sh breach on .delete( inside any fn sync_.

4

One store layer

Nineteen stores, no shared base — so the same three problems appear thirteen to fifteen times.

What is broken

  • record_id_key is pasted into 13 store modules.
  • 15 init_schema() methods, each called best-effort at boot: a failure logs and silently disables that store. Nothing reports "auth_store did not initialise", so a half-booted gateway looks healthy.
  • No schema version row and no migration mechanism. Opaque-JSON row bodies have absorbed every field addition so far, which works right up until a shape has to change.

The change

  • store_common.rs: record_id_key once, a StoreInit result type, and a schema_version row with a migrate(from, to) hook that is a no-op today — so the first real migration is not also the invention of the mechanism.
  • One startup store report: a single log summary plus a /api/health/stores entry listing each store as ready or degraded(reason).

Exit gate

  • record_id_key defined exactly once — grep count of 1.
  • Test: a forced init_schema failure appears in the startup report as degraded.

≈1–2 sessions · 13 store modules, mechanical

5

Compile once

The whole crate is compiled twice, on every check, by everyone.

What is broken

lib.rs declares 95 modules. main.rs declares 96 and references the library crate zero times. The bin target recompiles all 95 modules from scratch instead of linking the lib, and the CI check that keeps both mod lists in sync exists only to protect that duplication.

The change

  • The ~1,530 non-mod lines of boot logic move into the library as pub async fn run(args) -> Result<()>; main.rs becomes a shim that parses args and calls it. Visibility gets easier, not harder — the boot code ends up inside the crate it wires.
  • Delete the duplicate mod list and the CI check guarding it. Deleted, not skipped.

Exit gate

  • cargo check --workspace --all-targets wall-clock measured before and after and recorded in the commit body. Expect roughly half.
  • main.rs under 40 lines, with zero mod declarations.

6

state.rs stops being four files in one

3,253 lines doing four jobs — and the root cause of 20 of the 42 circular module pairs.

What is broken

state.rs holds 63 public type declarations (≈1,484 lines of definitions), 28 RwLock collection fields, and 40 ControlState methods, plus free helpers. The cycles are structural rather than accidental: every subsystem imports its types from state.rs, and state.rs imports their behaviour back.

The change

  • Step 1, types only. Move the 63 declarations into a domain/ tree, or crates/common where a type is genuinely shared. Purely mechanical, and it breaks most of the 20 cycles by itself because the dependency becomes one-way. One commit, reviewed for "only moves, no edits".
  • Step 2. Split the 40 methods by aggregate — tasks, entities, missions, feed — each in its own file. update_task from Phase 2 lands here naturally, and the 17 push-only sites finally get a creation method, which retires the Phase 2 allowlist.

Exit gate

  • state.rs under ~800 lines.
  • A script counting circular module pairs, run before and after, recorded in the commit body — target is those 20 pairs gone.
  • No module imports both a type and a function from state.rs.

≈2–3 sessions · wide diff, no behaviour change

7

One rule, one place

The residue, including the three corrected claims from the top of this page.

The change

  • derive_mission_task_counts becomes the only mission tally; the 18 inline mission_id filters call it. Move it out of orchestrator into the mission module it belongs to.
  • Renew the heartbeat lease while a dispatch is in flight, instead of betting the dispatch finishes inside ten minutes.
  • reminder_fired becomes a bool on every path; chat_tools.rs:1404 stops writing it as a string.
  • Decide explicitly whether two gateway instances against one SurrealDB is a supported topology. If yes, reminders need the lease treatment heartbeats already have. If no, say so in ARCHITECTURE.md and stop paying for half-measures.

Exit gate

  • One tally function; grep proves no inline mission-task filtering remains.
  • Test: a dispatch longer than the lease window cannot be re-fired.

How to run a phase

git switch main && git pull && git switch -c fix/phase-N-<slug>
# ... change ...
rustfmt --edition 2024 <only the files you touched>   # never `cargo fmt --all`
cargo check  --workspace --all-targets
cargo clippy --workspace --all-targets -- -D warnings
cargo test   --workspace
scripts/repo-health.sh --full

Then update STATUS.md with what became real, commit as fix(<scope>): <lowercase imperative> with a body explaining why, and merge before starting the next phase.

Out of scope for all seven phases: the Architect crate stays in shadow mode; no new features; no LLM behaviour changes; no renaming of consistent-world identifiers. The full checklist version of this plan lives in the repo at docs/plans/2026-09-13-hardening-plan.md.
